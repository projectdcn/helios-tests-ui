A · 34 cases

A way to read sideband control-session state

These cases assert facts about SPDM/IFCP control sessions: how many exist, which switch and ASIC terminate them, which link is the SelectedLink, and the control port. We found no way to read that. The node-agent REST API on the switch exposes only /api/health and /api/runtime/requests, and afmctl show port statistics ifcp reports only tx_errors (rx/tx counts stay 0).

  1. A command or API that lists every control session per GPU: GPU / accelerator id, terminating switch and ASIC, SelectedLink, standby links, control port, state, SPDM encryption on/off, IFCP version, sequence number.
  2. The per-switch view of the same sessions (for the per-switch count and load-balance cases).
  3. How to tell which of a GPU's links is currently the active control link, so we can flap that specific link (TRG-002/003).
  4. Whether IFCP rx/tx packet counters exist somewhere other than afmctl show port statistics ifcp.
  5. The Sideband / Node Manager view: registration, compatibility result and GPU reachability per compute.

IFCP packet capture and drop injection

These cases check frame formats, header flags, priorities, retransmits and behaviour when specific IFCP messages are dropped. The plan mentions OVS and tc u32 filters (for example on eth330 in the asic1 namespace), so AMD appears to have a working setup.

  1. The supported capture point for IFCP frames on the switch (netdev and namespace) and on the compute tray, with the ethertype or filter to use.
  2. The OVS / tc filter scripts used for TC-009…015 and TC-040…043, or the exact filter definitions.
  3. The IFCP frame and header specification (outer header flags, reserved bits, PCP, capability TLVs, datagram format) we should assert against.
  4. How to produce a minor-version mismatch (TC-CTRL-011, SBM-086): a test build or a packet-rewrite filter.

Observed on MR3

Behaviour to confirm

From the first automated AFM run on the MR3 mini rack (13 Oct, AFM 0.1.0-AICC-797, 46 pass, 13 fail). Please tell us whether each is intended.

Read access is open to every authenticated user. A user whose role grants only the cluster group can read auth users and monitoring alerts (HTTP 200). Writes outside the granted groups are refused (403). Is read RBAC enforced by design?

An idle AggWatch stream closes after about 32 seconds with {"type":"Error", ... "stream error: EOF"}. Is there an idle timeout, and should clients send keepalive pings? (Plan case AGGW-020 expects an idle connection to stay open.)

Telemetry queries are rate-limited. About 30 queries in a few seconds returned HTTP 413 "query rate limit exceeded". What is the documented limit?

Empty or malformed watch options return a code 500 Error event before the stream closes. Should that be a 4xx-style error?

Audit records for AggWatch connections (AGGW-017/018): what action name and fields does the audit record of a watch use?
