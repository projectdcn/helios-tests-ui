How to run the Helios rack tests

How to run on a mini rack (MR3: 1 switch tray, 2 compute trays) and on a full rack (6 switch trays, 18 compute trays), based on the MR3 runs and the g02-g17 full-rack execution log.

Common setup Quick start Without a rack Mini rack (MR3) Full rack AFM controller API Specific cases Results HTML report Coverage

0Common setup (once per runner machine)

The runner needs SSH access to every switch and compute. It also needs ipmitool, but only for the DC power-cycle test (brew install ipmitool).

cd ~/dev/helios-tests
python3 -m venv .venv && .venv/bin/pip install -e '.[tools,dev]'

Node requirements

  • Passwordless sudo on switches and computes. Tests use sudo -n, so a sudo password makes those checks fail with "a password is required".
  • Same tool paths on every compute: TransferBench, rccl-tests and RcclSmokeTest.
  • NTP synced. MR3 is currently unsynced (c1 is 131 s off). That fails TC-CTL-035 and makes AFM event timing unreliable.

Login: SSH keys (recommended) or passwords

Install your key once per node with ssh-copy-id and set key_file in the inventory (MR3 does this); then no passwords are needed. Otherwise use password_env and enter the passwords as below.

Passwords: enter them yourself in each new terminal

read -s shows nothing as you type and keeps the password out of shell history. Inventories only name the environment variables; no password is stored in a file.

read -s "HELIOS_SWITCH_PASSWORD?Switch password: " && export HELIOS_SWITCH_PASSWORD && echo
read -s "HELIOS_COMPUTE_PASSWORD?Compute password: " && export HELIOS_COMPUTE_PASSWORD && echo

Only needed for the DC power-cycle test:

read -s "HELIOS_BMC_PASSWORD?BMC password: " && export HELIOS_BMC_PASSWORD && echo

Only needed for the AFM controller API tests (tests/afm):

read -s "HELIOS_AFM_PASSWORD?AFM admin password: " && export HELIOS_AFM_PASSWORD && echo
Scope today: 400 of the 542 plan cases are automated, plus 2 RCCL smoke tests. 52 of them (MCH rack, LDAP/RADIUS, syslog, upgrade images, management-network control) skip until the equipment is in the inventory.
  • Over SSH: switch hardware, switch agent, datapath, scale-out RDMA, RAS reset, metrics exporter, node platform, sideband and IFCP.
  • Over the AFM REST API and AggWatch WebSocket (tests/afm, 233 cases): auth, cluster and object specs, failover policies, RBAC, audit, metrics, techsupport and AggWatch. Plus 149 disruptive cases, built from the full-rack procedures: compute Reconfigure, agent/controller restarts, vPOD/compute/switch lifecycle, fabric-link failover (TC-AFM-006…047, RC-001…026), the FO failover scenarios and vPOD operations (TC-E2E), controller resilience, snapshot/restore, bug regressions, stress, compute-side afmctl checks, IFCP recovery, switch-agent cases and traffic with AFM operations.

1Quick start: what to run, from where, on which rack

With or without AFM

Only tests/afm talks to the AFM controller (REST + AggWatch). Every other suite works over SSH alone: SONiC on the switches, afmctl on the compute trays. The rack still needs AFM running either way, because AFM programs the fabric that the datapath tests use; those tests just don't call its API.

Mini rack (MR3): everything from your Mac

3Mini rack (MR3: 1 switch, 2 computes)

The inventory inventory/mr3.local.yaml is git-ignored and holds no passwords. It's already calibrated from the two MR3 runs and the full-rack log:

AreaSetting
L2 pingmode: afmctl: accelerator IDs and LINK_UP ports are discovered at run time with afmctl show device/port --json. Nothing is hard-coded.
TransferBenchTransferBench a2a 1G per tray. Cross-domain runs socket multi-rank (TB_RANK / TB_MASTER_ADDR), so the trays don't need to SSH to each other.
RCCLrccl-tests *_perf, 1K to 1G, per tray. Cross-domain goes through mpirun and needs passwordless SSH from c1 to c2.
RCCL smokeRcclSmokeTest with NCCL_IB_DISABLE=1 NCCL_CUMEM_ENABLE=0 LD_LIBRARY_PATH=/opt/rocm/lib:/opt/rocm/lib/rocm_sysdeps/lib. The full rack failed without these.
Switch (QFX5252)CPLDs are matched by description; the "PDB HSC" power entries are exempt from the FRU and load-share checks; Ethernet513/514 are 100G uplinks.

Run it in stages, and only move on when the previous stage is clean.

Stage 1: read-only health (changes nothing)

.venv/bin/pytest tests --inventory inventory/mr3.local.yaml -m "not stress" -v --log-file=results/mr3-health.log
MR3 state as of 2026-10-13 (real rack issues, not test problems):
  • Switching plane 9 (VLAN 1000, asic1): black-holes port 9 on all 8 GPUs, so every datapath test is BLOCKED. TC-SWA-074 shows the drops.
  • TC-BU-011 / TC-SWH-030: c2 GPU 0003 ports 12, 32 and 33 are down.
  • TC-CTL-035: NTP isn't synced.
  • TC-CTL-139 to 148: the metrics exporter isn't running.
  • c2 down (13 Oct, evening): no ping or SSH from the host (.86) or its BMC (.87); st1 runs only slot 0's sb-node-agent.
Datapath pre-flight gate. Every IFoE traffic test first checks, once per run:
  • every compute answers SSH and all GPUs are ACTIVE
  • one afmctl L2 ping per GPU over every LINK_UP port
  • no cabled switch port is dropping more than 100 frames/s
If anything fails, those tests report BLOCKED with the reason, instead of hanging. This exists because of MR3's broken switching plane.

Stage 2: datapath (sends traffic, changes no configuration)

.venv/bin/pytest tests/l1/test_rccl_smoke.py tests/l1/test_afm_datapath.py tests/hw/test_hw.py --inventory inventory/mr3.local.yaml -v --log-file=results/mr3-datapath.log

It runs the RCCL smoke gate first, then L2 ping (ring pairs, about 30 s per ping), TransferBench, and the RCCL sweeps up to 1G.

Stage 3: disruptive tests, one case at a time

.venv/bin/pytest tests --inventory inventory/mr3.local.yaml --allow-disruptive --tc TC-SWA-140 -v --log-file=results/mr3-disruptive.log

Suggested order, from least to most disruptive:

  1. Container restart: TC-SWA-140.
  2. SWSS restart: TC-SWA-141.
  3. Datapath reset: TC-RAS-reset-001, 003.
  4. OS reboot: TC-RAS-reset-007.
  5. DC power cycle: TC-RAS-reset-008.

The IFoE driver tests (TC-AFM-LU-001, TC-HW-017) skip until a module name is set. The full-rack log only shows amdgpu, so ask AMD whether there's a separate IFoE module.

Stage 4: AFM controller API (REST + AggWatch)

See AFM controller API for the curl connectivity check. The AFM controller runs on the switch tray (https://10.153.80.83, API guide at /docs/). The afm: section of the inventory names the admin user; the password comes from HELIOS_AFM_PASSWORD, which you export yourself in the same terminal. Without it, only the unauthenticated cases run (RC-021, CTL-089, AGGW-003/004, CTL-004) and the rest SKIP.

read -s HELIOS_AFM_PASSWORD && export HELIOS_AFM_PASSWORD
.venv/bin/pytest tests/afm --inventory inventory/mr3.local.yaml -v --log-file=results/mr3-afm.log

Non-disruptive: reads, plus throw-away objects named helios-<tc>-* (failover policies, alert policies, test users / roles / role-bindings, empty vPODs). These are deleted after every test, even a failing one. No GPU, link or vPOD membership is touched. The run takes about 10 minutes; the AggWatch idle, no-options and burst cases are the slow ones.

Disruptive (needs --allow-disruptive; each one first checks AFM health and reports BLOCKED if AFM is unhealthy):

  • TC-AFM-035A (safest first): drain, decommission and delete of the only switch must all be rejected with 412.
  • Compute Reconfigure: RC-001…006, 017, 019, 020, 026. Each resets the tray's GPUs.
  • Agents and controller: TC-AFM-006, 007, 018, 019, 020. 021 and 022 skip with one controller.
  • vPOD and compute lifecycle: TC-AFM-010, 036…038 (stop afm-agent on every switch), 045…047 (decommission, delete and readmit a compute).
  • Fabric links: TC-AFM-011…017, 039…042. These shut one trunk port that is cabled to a GPU; list ports to leave alone in thresholds.afm.avoid_ports.
  • Switch lifecycle TC-AFM-023…035 needs at least 2 switches, so it skips on MR3.
  • Failover scenarios and vPOD operations: TC-E2E-025…146 (25 cases, in test_afm_failover.py). FO-013, 014, 024 and 033 need a GPU with 2–3 stations up. Station of a GPU port = port // thresholds.afm.ports_per_station (2). Verified on MR3 c1 with afmctl show station: station k is ports 2k and 2k+1.

Run them one at a time with --tc. Several move compute trays out of the system vPOD, so expect traffic interruptions. On MR3 the plane-9 datapath fault doesn't block these cases: they check AFM state, not traffic.

.venv/bin/pytest tests/afm --inventory inventory/mr3.local.yaml --allow-disruptive --tc TC-AFM-035A -v

Every request and response goes into the per-test log, so it shows up in the HTML report. Passwords and session ids are redacted. Tune the mini-rack expectations under thresholds.afm: quorum_members, build_version, system_policy, max_not_ready_ports_per_compute, metrics.known_no_series, reconfigure_timeout_s, aggwatch.* timings. For the disruptive cases: vpod_test_computes (1, or all like the full-rack runs), target_compute, avoid_ports, readmit_timeout_s (300; AIFM-1512 showed 124–134 s) and plane_restore_s.

5AFM controller API (both racks)

The tests/afm suite talks to the AFM controller over HTTPS: REST and the AggWatch WebSocket. It doesn't SSH to any tray, so it only needs the controller URL, the admin user and HELIOS_AFM_PASSWORD exported in the same terminal.

1. Full rack only: open the tunnel

Keep this running in its own terminal. The browser UI at https://localhost:8443/#/login uses the same tunnel.

ssh -N -L 8443:10.190.198.51:443 <user>@<jump-host>

2. Check that curl reaches the API

Set the controller URL for the rack you're checking. MR3:

AFM=https://10.153.80.83

Full rack:

AFM=https://localhost:8443

Without credentials, the API must answer 401. 000 means there's no connection: the tunnel is down or the port is wrong.

curl -sk -o /dev/null -w '%{http_code}\n' $AFM/configs/cluster/v1/version

With the password exported, the login must print login: 200, and the next two calls must return JSON: the build version, then the cluster status with healthy: true and the quorum members.

curl -sk -c /tmp/afm.jar -o /dev/null -w 'login: %{http_code}\n' -H 'Content-Type: application/json' -d "{\"username\":\"admin\",\"password\":\"$HELIOS_AFM_PASSWORD\",\"tenant\":\"default\"}" $AFM/v1/login
curl -sk -b /tmp/afm.jar $AFM/configs/cluster/v1/version
curl -sk -b /tmp/afm.jar $AFM/configs/cluster/v1/cluster | python3 -m json.tool | head -40

Delete the session cookie when you're done:

rm -f /tmp/afm.jar

7Results (both racks)

Each run creates a folder results/<rack>-<timestamp>/ containing:

FileContents
tc_summary.csvOne PASS / FAIL / BLOCKED / SKIP / PARTIAL verdict per plan ID. BLOCKED means a pre-flight refused to start: the datapath gate (traffic tests), the RDMA gate (scale-out) or the AFM health gate (disruptive AFM tests).
tc_results.csvOne row per test item: suite, test, description, outcome, duration, start time, failure message, measured values, and the path to its log.
logs/NNN_<test>.logThe trace of that one test: every command (or AFM request/response, secrets redacted), its output, exit code and timing.

The --log-file records every command, its output, exit code and duration. Passwords are never logged.

Access needed per case

tools/access_needed.py adds an Access needed column to the workbook: column I on Testcases, column H on mortaro. It says what each case needs to run: AFM API, switch SSH, compute SSH, datapath traffic, BMC/PDU, a special rack or server, or manual work. Automated cases are classified from the code; the rest from the plan category and title, and values inferred from a title only are marked "(est.)". Close the workbook in Excel first.

.venv/bin/python tools/access_needed.py testplan/full_rack_testplan.xlsx
.venv/bin/python tools/access_needed.py --summary

To also rewrite the Automation column (D) from the code, add --automation with the rack result folders. Yes means automated and run on a rack (any result, including Skipped), Inprogress means automated but never run on a rack, and No means not automated.

.venv/bin/python tools/access_needed.py testplan/full_rack_testplan.xlsx --automation results/mr3-2026101*

Record the results in the test-plan workbook

tools/update_testplan.py writes the verdicts of one or more runs into the Testcases sheet: Execution Status (F), SW Version (G) and Execution Notes (H). Only rows of the plan IDs that ran are changed. Close the workbook in Excel first; the tool refuses while Excel's ~$ lock file exists. It saves a timestamped backup next to the workbook before writing.

.venv/bin/python tools/update_testplan.py testplan/full_rack_testplan.xlsx results/<run> [more runs] --sw-version "AFM 0.1.0-AICC-817" --label "g02-g17 full rack, <date>" --dry-run

Drop --dry-run to write.

Run verdictExecution StatusNotes
Any item failedFAILfirst failure reason
All executed items passedPASSitems passed, plus any skipped
BLOCKED by a pre-flightPending"Blocked: " + the reason
Not executed (SKIP)untoucheduse --mark-skipped to write Pending + reason

Several runs merge like the HTML report: a run that executed a test beats one that skipped it, otherwise the later run wins. The rows with a shared or missing ID are handled (TC-AFM-005 RCCL vs Failover CRUD, TC-AFM-048 Audit vs Techsupport, TC-AFM-035A). The Execution Summary counts recalculate when Excel opens the file.

Updating the workbook: close it in Excel first. A script writing the file while Excel has it open loses its changes when Excel saves. The g02-g17 full-rack results (10–12 Oct: AFM L2 batch and the 18-tray traffic validation) are already recorded in it.

8HTML report (summary + per-test logs)

Turn one or more runs into a single self-contained HTML page: a summary dashboard on top, then every test case with its own command log.

  1. Find the run folders. Every pytest run writes results/<rack>-<timestamp>/. Newest first: 
    ls -td results/*-2*/ | head
  2. Optional: write the key findings to a text file, one per line. Start a line with ! for a problem or + for good news; anything else is neutral: 
    ! Switching plane 9 broken: port 9 black-holes traffic on all GPUs
! NTP not synchronized on any node
+ Control plane healthy: agents connected, IFCP up, topology matches cabling
Not run: RAS power-cycle tests (disruptive)
  3. Generate the report: 
    .venv/bin/python tools/html_report.py results/<run-folder> [more run folders] -o results/report.html --title "..." --subtitle "..." --notes results/findings.txt

    For example, today's MR3 report merges the full read-only run, the stage-3 run and the RDMA run:

    .venv/bin/python tools/html_report.py results/mr3-20261013-071856 results/mr3-20261013-072136 results/mr3-20261013-075720 -o results/MR3-Test-Report.html --title "Helios MR3 Test Report" --subtitle "QFX5252 st1 + 2 compute trays" --notes results/mr3-findings.txt
  4. Open it in a browser: 
    open results/report.html
OptionMeaning
results/<run-folder> …One or more run folders. When the same test appears in several, a run that actually executed it (pass, fail or blocked) wins over one that skipped it; otherwise the later run wins.
-oOutput HTML file (required).
--title / --subtitlePage title, and the line under it (rack, versions, etc.).

DashboardBanner (rack, runs, times, executed result), counts (test cases, passed, failed, blocked, skipped, test items), result doughnut, per-suite bar chart

Logs per test exist for runs made from 2026-10-13 onward. The charts load Chart.js from a public CDN, so they need internet access. Reports contain lab hostnames and IPs, so keep them in the git-ignored results/ folder.
