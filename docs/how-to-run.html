How to run the Helios rack tests

How to run on a mini rack (MR3: 1 switch tray, 2 compute trays) and on a full rack (6 switch trays, 18 compute trays), based on the MR3 runs and the g02-g17 full-rack execution log.

0Common setup (once per runner machine)

The runner needs SSH access to every switch and compute. It also needs ipmitool, but only for the DC power-cycle test (brew install ipmitool).

cd ~/dev/helios-tests
python3 -m venv .venv && .venv/bin/pip install -e '.[tools,dev]'

Node requirements

  • Passwordless sudo on switches and computes. Tests use sudo -n, so a sudo password makes those checks fail with "a password is required".
  • Same tool paths on every compute: TransferBench, rccl-tests and RcclSmokeTest.
  • NTP synced. MR3 is currently unsynced (c1 is 131 s off). That fails TC-CTL-035 and makes AFM event timing unreliable.

Login: SSH keys (recommended) or passwords

Install your key once per node with ssh-copy-id and set key_file in the inventory (MR3 does this); then no passwords are needed. Otherwise use password_env and enter the passwords as below.

Passwords: enter them yourself in each new terminal

read -s shows nothing as you type and keeps the password out of shell history. Inventories only name the environment variables; no password is stored in a file.

read -s "HELIOS_SWITCH_PASSWORD?Switch password: " && export HELIOS_SWITCH_PASSWORD && echo
read -s "HELIOS_COMPUTE_PASSWORD?Compute password: " && export HELIOS_COMPUTE_PASSWORD && echo

Only needed for the DC power-cycle test:

read -s "HELIOS_BMC_PASSWORD?BMC password: " && export HELIOS_BMC_PASSWORD && echo

Only needed for the AFM controller API tests (tests/afm):

read -s "HELIOS_AFM_PASSWORD?AFM admin password: " && export HELIOS_AFM_PASSWORD && echo
Scope today: 435 of 577 cases are automated (the 542 plan cases, 23 switch-tray cases added on 14 Oct, TC-SWH-037…059, and the 12 health checks added on 15 Oct, HC-000…011), plus 2 RCCL smoke tests used as evidence. tools/coverage.py gives the current numbers. 52 of them (MCH rack, LDAP/RADIUS, syslog, upgrade images, management-network control) skip until the equipment is in the inventory.
  • Over SSH: switch hardware, switch agent, datapath, scale-out RDMA, RAS reset, metrics exporter, node platform, sideband and IFCP.
  • Over the AFM REST API and AggWatch WebSocket (tests/afm, 233 cases): auth, cluster and object specs, failover policies, RBAC, audit, metrics, techsupport and AggWatch. Plus 149 disruptive cases, built from the full-rack procedures: compute Reconfigure, agent/controller restarts, vPOD/compute/switch lifecycle, fabric-link failover (TC-AFM-006…047, RC-001…026), the FO failover scenarios and vPOD operations (TC-E2E), controller resilience, snapshot/restore, bug regressions, stress, compute-side afmctl checks, IFCP recovery, switch-agent cases and traffic with AFM operations.

2. Check that curl reaches the API

Without credentials, the API must answer 401. 000 means there's no connection: the tunnel is down or the port is wrong.

curl -sk -o /dev/null -w '%{http_code}\n' $AFM/configs/cluster/v1/version

With the password exported, the login must print login: 200, and the next two calls must return JSON: the build version, then the cluster status with healthy: true and the quorum members.

curl -sk -c /tmp/afm.jar -o /dev/null -w 'login: %{http_code}\n' -H 'Content-Type: application/json' -d "{\"username\":\"admin\",\"password\":\"$HELIOS_AFM_PASSWORD\",\"tenant\":\"default\"}" $AFM/v1/login
curl -sk -b /tmp/afm.jar $AFM/configs/cluster/v1/version
curl -sk -b /tmp/afm.jar $AFM/configs/cluster/v1/cluster | python3 -m json.tool | head -40

Delete the session cookie when you're done:

rm -f /tmp/afm.jar

4. The four tabs

  • Run: pick the rack, then either the health check (on g02-g17 it passes --known testplan/health-known.yaml, like run-health.sh) or cases: TC ids, a marker expression (e.g. healthcheck), or a test-plan pick (section 6). Pick from the test plan: the Level, Scope, Disruptive, Health check, Origin and Status filters are dropdowns of checkboxes with the values the workbook actually has (a blank status shows as (not run); nothing ticked = no filter; Tab / Enter / Space / Esc work), plus Suite (all / afm / ssh). About half a second after a filter change the matching automated cases are listed below (ID, title, level, scope, disruptive, health, last status), all ticked, and the ticked ones fill the test case ids box ("N case(s) from <workbook>"); untick single cases, search by id or title, Select all / Select none (on the cases shown); "k of n selected" counts them, and matching cases without a test are only counted. Ids you typed or edited yourself are never replaced silently: a filter change or a tick then offers Replace the test case ids with the N picked case(s) instead. Fill the test case ids reads the workbook again, ticks every matching case and fills the box. Loading a preset, Run again and the remembered form restore the filters and exactly the saved ids (the listed cases among them are ticked). The matching is tools/select_cases.py's own (case-insensitive exact). The pick reads (read only) the rack's workbook: from ui/racks.yaml, by default ~/dev/helios-tests/testplan/full_rack_testplan.xlsx for all three profiles, once per change of the file; a workbook without the full-rack columns (Scope, Origin, Disruptive, Health check) is refused instead of filtering on the wrong columns. Optional switch / compute subsets. allow disruptive cases asks for confirmation (disruptive batches still need the GO health check and the per-batch approval). Type the AFM password, then Start run. One run at a time per rack; a second one queues. Save as preset… stores the current selection under a name (letters, digits, space, - _ ., at most 60; saving over an existing name asks first) for the rack picked; Load preset fills the form from one and Delete preset removes it. A preset is checked like a run (a selection a run would refuse cannot be saved). The browser also remembers the form you last used per rack. Save as default makes the current form (everything but the password; checked like a preset) the rack's default. Which form the Run tab opens with (first visit, reload, or picking another rack): the rack's saved default if there is one, else the form last used in this browser, else the original form (health check, --known ticked, no ids / marker / filters, test paths tests, no subsets, disruptive off, no extra arguments, password empty). Reset to default puts the original form back and then asks whether to also delete the rack's saved default and the form remembered in this browser, so the next visit opens with the original form too; it never touches the presets. AFM password in the macOS Keychain (opt-in): tick Remember in macOS Keychain for <rack> and start a run with the password typed: it is saved first (login Keychain, service helios-ui, account <rack>:<AFM user>, the user being afm.auth.username of the inventory, default admin), and the status shows saved in Keychain. A later run (or Re-run failed) with the password field empty uses it; the log header then says AFM password from macOS Keychain (memory only). A typed password always wins over the saved one. Forget saved password deletes it. Only printable ASCII passwords can be saved (type others each time); if the Keychain cannot be used (not macOS, locked, refused) the page says so and the run goes ahead without it.
  • Sessions (Run tab, Session box): for running one test case at a time and still getting one result. The box shows the rack's current session: its name, when it started and how many runs it has (with the consolidated count, e.g. 12 cases: 9 PASS 2 SKIP 1 FAIL). Every run started from the UI on that rack joins the current session; if the rack has none yet, the first run starts one named by date and time (e.g. 16 Oct 21:58). New session… asks for a name (default: the date and time; letters, digits, space, - _ ., at most 60) and makes it the current one: the next runs go there, the old session stays as it is. After every run that joins it, the session's consolidated folder <results_dir>/<rack>-session-<YYYYmmdd-HHMMSS>/ is built again: one row per test with its latest result across the session's runs, by the rule of tools/html_report.py: an executed result (pass / fail / error / partial) beats a skip or a pre-flight block, otherwise the later run wins. So FAIL then PASS gives PASS, and PASS then SKIP (e.g. a re-run without the AFM password) keeps the PASS. The folder has tc_results.csv, tc_summary.csv (verdicts computed like a normal run's), each test's command log under logs/<run>/, session.json (name, start, the runs, and for every test which run its result came from) and report.html (title <rack> session <name>; each row names its run). Health runs in a session keep their own health.json / health.html; the session report just includes their test rows. A Re-run failed adds its plain re-run (not the -merged folder).
  • Case history: type a test case id; every run of it on every rack, newest first, with result, message and links to the test's log and the run's report (from results/index.csv, section 7).
  • Runs & live log: running and queued runs with the streamed log (also saved under results/runs/<rack>/ui-runs/ of the main checkout). Stop a running one (on the jump host this kills the remote process too) or cancel a queued one. Download log saves the log as <run-id>.log.txt (for a running run: what is there so far). Run again fills the Run tab with that run's settings (rack, health check or cases, TC ids, marker, test-plan pick, subsets, disruptive, --known) and switches to it; nothing starts: check it, type the AFM password and Start run (a Re-run failed run opens the re-run box of the Results tab instead). If the run's rack is no longer in ui/racks.yaml the page says so and fills nothing.
  • Results: at the top, Sessions: one entry per session of the rack (newest first, the current one marked) with its name, the number of runs (open it for the list of runs, each linked to its report), the consolidated cases (12 cases: 9 PASS 2 SKIP 1 FAIL), when the folder was written, session report, session.json, Download results (.zip) (the whole session folder) and Rebuild (build the folder and its report again from the runs). Below, as before, every results folder of the rack (the session's runs are still listed one by one; session folders are not repeated there) with its health verdict, links to health.html / report.html (built on the Mac for jump-host runs), Build report, and Re-run failed on a health run that is not GO (runs --rerun-failed: re-runs what did not pass, merges it with that run and every run merged into it before, and judges again). Download results (.zip) saves the whole folder (tc_summary.csv, tc_results.csv, logs/, health.*, reports; symbolic links and anything outside the folder are left out); Download report / Download health report save report.html / health.html alone.
  • Inventory & quarantine: Form (rack / AFM settings, switch and compute tables, thresholds) or Raw YAML (keeps comments; a form save rewrites the file without comments, the preview warns). Preview changes validates with the real inventory loader, checks unique names, hosts, BMCs and slots, refuses password values (use password_env / key_file) and shows the diff; Save writes a dated backup <file>.bak-YYYYmmdd-HHMMSS first and refuses if the file changed since it was loaded. Quarantine… on a node (reason required, optional until date) writes its quarantine: entry and Lift removes it; give a quarantined compute its AFM slot so the AFM-side checks can drop it. A compute tray without slot (or afm_name) cannot be quarantined: set the slot first (Compute trays table or raw YAML), then quarantine. After any Preview, nothing is written until Save (dated backup first) - the preview says NOT SAVED YET until then. For g02-g17 this changes the local copy only; the jump host gets it with the next run.

6. AFM password

Typed in the browser for each run (or, opt-in, taken from the macOS Keychain when the field is empty) and kept in memory for that run only. The run gets it through the variable the inventory names (afm.auth.password_env, default HELIOS_AFM_PASSWORD); on the jump host it goes to the remote shell's stdin, as read -s does. It is never written to a file, a command line or the log (a log line containing it shows <REDACTED>; the same for a password taken from the Keychain). The UI talks to the Keychain through /usr/bin/security: saving writes the command to security -i on its standard input with the password hex-encoded (nothing on a command line that ps could show), reading uses find-generic-password -w, which prints it to the UI only. Without it the AFM cases skip and a health run is INCOMPLETE.

7. Before the first full-rack run from the UI

  • Start with selftest, then MR3, then g02-g17. The jump-host part is unit-tested with a simulated SSH connection only, so watch the first g02-g17 run from the live log.
  • Never start a g02-g17 run from the UI while a manual run is going (run-health.sh, run-datapath.sh, ...): the UI run replaces ~/helios/helios-tests and ~/helios/fullrack-jump-afm.yaml on the jump host.
  • Only committed code reaches the jump host (HEAD of the UI checkout): commit before you run. Keep the branch merged with main so the jump host does not get older test code than the manual runs use.
  • Inventory edits made on the jump host by hand are replaced by the local copy at the next UI run (a .bak is kept): fetch it again with the scp above after any manual change there.

9. Install on a Linux server

The same UI can run on a Linux server (x86_64, python3 3.10, 3.11 or 3.12 with the venv module; Debian / Ubuntu: python3-venv), installed for your user, no root, no internet needed on the server. The bundle carries the committed code and every Python package as Linux wheels.

Build the bundle on the Mac (needs PyPI access; packs the committed HEAD of the UI checkout, without the workbooks, local inventories, results/ or backups):

cd ~/dev/helios-tests-ui && ~/dev/helios-tests/.venv/bin/python tools/build_ui_installer.py
# -> dist/helios-ui-<date>-<sha>.tar.gz  (~18 MB: app/, wheelhouse/ for 3.10-3.12, install.sh, uninstall.sh, README-INSTALL.txt)

Copy it and install:

scp dist/helios-ui-<version>.tar.gz <user>@<server>:
ssh <user>@<server>
tar -xzf helios-ui-<version>.tar.gz && helios-ui-<version>/install.sh

Options: --prefix DIR (default ~/helios-ui), --host ADDR (default 0.0.0.0: every address of the server; 127.0.0.1: the server only, open it through an SSH tunnel), --port N (default 8765; refused if another program has it), --python /usr/bin/python3.11, --online (pip from PyPI instead of the wheelhouse), --no-systemd, --dry-run (prints what it would do). It checks Linux, the Python version, the venv module and the free space, then creates app/ (the code), venv/, config/racks.yaml (starter profiles: the same three racks, with inventories, results and the workbook under data/), data/results/runs/<rack>/, data/inventories/, data/testplan/, logs/helios-ui.log and bin/, and starts the UI: as the systemd --user service helios-ui.service where there is one (it prints whether linger is on; without it the service stops when you log out: an admin runs sudo loginctl enable-linger <you> once), else with nohup through ~/helios-ui/bin/helios-ui {start|stop|restart|status|logs}. At the end it checks that http://127.0.0.1:<port>/ answers and prints the version (venv/bin/python -m ui --version prints it too).

Copy what the racks need (the installer copies no secrets and creates no keys):

  • ~/helios-ui/data/inventories/mr3.local.yaml and fullrack-jump-afm.local.yaml (the jump host's ~/helios/fullrack-jump-afm.yaml), ~/helios-ui/data/testplan/full_rack_testplan.xlsx.
  • SSH keys in ~/.ssh of the server user: one the jump host accepts (ssh -p 8059 tenant-hpe@165.204.38.103 true must work with no prompt) and the MR3 keys. The service has no ssh-agent: the key must be usable without a passphrase prompt.
  • No macOS Keychain on Linux: the page says macOS Keychain not available on this system, the Remember box is disabled; type the AFM password in the Run form for each run.

Open it: http://<server>:8765/ (install.sh prints the exact URL and the server's addresses). python -m ui --host ADDR (or HELIOS_UI_HOST) sets the address; on the Mac it stays 127.0.0.1.

The UI has no login. Anyone who can reach that port can start runs on the racks (disruptive ones included) and read every result. Restrict the port with the host firewall to the team's subnet. install.sh never changes the firewall; when firewalld or ufw is active and the port is not open it prints the command an admin would run (e.g. sudo ufw allow from 10.0.0.0/24 to any port 8765 proto tcp, or the firewall-cmd --add-rich-rule equivalent). To keep it on the server only: install.sh --host 127.0.0.1, then from the laptop ssh -L 8765:127.0.0.1:8765 <user>@<server> and http://127.0.0.1:8765/ (ssh -L 8780:127.0.0.1:8765 ... if 8765 is taken on the Mac by your local UI). The page accepts the server's host names and addresses only (no DNS rebinding); a DNS alias goes into ~/helios-ui/config/ui.env as HELIOS_UI_ALLOWED_HOSTS=alias1,alias2.

Upgrade, roll back, uninstall:

helios-ui-<newer>/install.sh                 # upgrade: app/ + venv/ replaced, config/ + data/ kept, old ones kept as app.prev / venv.prev
~/helios-ui/bin/install.sh --rollback        # back to app.prev (again = forward)
~/helios-ui/bin/uninstall.sh                 # service, app/, venv/, bin/ removed; config/, data/, logs/ kept
~/helios-ui/bin/uninstall.sh --purge         # everything (asks; --yes does not)

An upgrade refuses while a run is queued or running (--force stops it), waits for the old UI to exit before it checks the port, keeps the port and address of the installation (one made before --host existed becomes 0.0.0.0; give --host to choose) and prints the old and new versions and how many code files changed. The installed UI keeps the code and the data apart: every result, session, preset, default and run log goes to the profile's results_dir under data/; command-line runs on the server follow HELIOS_RESULTS_ROOT (the service sets it; cd ~/helios-ui/app && HELIOS_RESULTS_ROOT=~/helios-ui/data/results ../venv/bin/python -m pytest ...). g02-g17 runs from the server send the installed code (the files of app/MANIFEST.txt, the commit the bundle was built from) to the jump host instead of git archive: upgrade the server to send newer code.
